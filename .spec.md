# Spec: provider usage rate-limit resilience

## Target

The AI Usage Tracker polls two provider endpoints (Claude Code, Zcode). Anthropic's
`/api/oauth/usage` rate-limits aggressively and currently answers 429 with `retry-after: 0`
even to a cold request. Today this causes:

- The popup banner "Provider rate limited this check. Automatic retry in five minutes."
- The tray title shows `Cl --` whenever the last check failed, even though last-known
  windows are cached and the popup still renders them ("Last known usage").

Goal: fewer requests to the provider, and the tray keeps showing the last-known number
(marked as approximate) while the data is still usable.

## Negative spec (what this change does NOT do)

- No per-provider request when the cache is younger than its TTL, even with force.
- No retry-after shorter than the computed backoff (retry-after can only lengthen a wait).
- No display of last-known values older than 1 hour, or whose window has already reset.
- No change to which windows feed the tray (5-hour / Weekly labels only) or to Codex
  account usage handling.

## Behavior

1. Success cache TTL: 60s → 300s. All pollers (tray loop, popup, main window, web
   dashboard) coalesce through it.
2. Error backoff: consecutive failures double the retry delay, 300s → 600s → 1200s,
   capped at 1800s; a `Retry-After` header longer than the computed delay is honored;
   success resets the streak.
3. Manual refresh (panel and popup buttons) passes `force`, which bypasses the TTL and
   backoff but never sends more than one request per 60s per provider.
4. Tray title: `tray_remaining` keeps returning the minimum remaining % of the canonical
   windows while the value is at most 3600s old and no window reset has elapsed, even if
   the latest check failed. A separate `tray_value_is_stale` reports error/staleness so
   the title prefixes `~` (e.g. `Cl ~92%`) while the panel banner still explains why.
   Beyond 3600s or after a window reset the tray shows `--` again.
5. Tooltip updated to explain `~ = last known value`.
6. Persistence: the whole provider cache state (usage only, keyed by a token
   fingerprint, never the token) is written atomically to
   `~/.codex-switcher/provider-usage.json` after every refresh cycle. A cold start
   seeds the cache from it when the fingerprint matches and the data is within the
   same 3600s bound, so a restart during a rate-limit storm keeps showing
   `Cl ~NN%` instead of `Cl --`. Cache-hit cycles rewrite the full state so a
   provider that was not refreshed this cycle is not erased from disk.

## Edges

- `not_connected` providers have no `updated_at` and no windows → `--` (unchanged).
- Negative clock skew (age < 0) counts as fresh.
- Force refresh during error backoff is allowed (user-driven) with the same 60s floor.
- `retry-after` values that fail to parse as seconds are ignored.

## Verification

- Rust unit tests: stale-window boundaries, backoff table, force/floor decision.
- cargo test on the Mac (harness lacks GTK/webkit for the tauri lib).
- Build and deploy to /Applications on the Mac; tray shows `Cl ~NN%` during a live 429.
